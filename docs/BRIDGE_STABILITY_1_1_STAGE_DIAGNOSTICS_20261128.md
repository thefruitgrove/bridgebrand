# BRIDGE Stability 1.1 — 관리 대시보드 작업별 장애 진단

적용 기준일: 2026-11-28

## 현장 문제
기존 관리자 대시보드에서는 전체 정상·복구·장애 여부와 공개 데이터 일치 여부를 확인할 수 있지만, 점수 계산인지 DB 발행인지 Cloudflare 반영인지 장애 발생 단계를 관리자에게 곧바로 보여주지 못한다.

## 이번 보강
기존 09:30 KST 종합점검에서 GitHub Actions의 완료된 정규 수집·기존 근거 복구·재수집 판단·실서비스 검증 작업의 **당일 실행 기록**을 읽는다. GitHub 공개 저장소의 정상 main 브랜치에 해당하는 정기 실행과 수동 실행만 채택하며 QA 브랜치 실행은 제외한다.

- 각 작업의 최신 상태, 실행 횟수, 실패 횟수, 해당 Actions 실행 페이지를 연결한다.
- 실패한 작업은 GitHub Jobs 단계 결과를 추가로 조회하여 사전 등록된 단계 명칭(뉴스 수집, DART 수집, 점수·순위, DB 발행, JSON 생성, 400건 정합성, Cloudflare 배포 요청 등)으로 장애 위치를 표기한다.
- GitHub 로그 원문·Secret·환경변수·개별 평가대상 원장·실패 예외 상세는 관리자 HTML에 포함하지 않는다.
- 당일 실행이 없으면 '기록 없음', 확인 불가능한 실패 단계는 '단계 확인 불가'로 표시한다. 단계 추정으로 성공이나 오류 원인을 만들어내지 않는다.
- 기존 GitHub Actions artifact에 통합되며 운영 홈페이지 `site/`에는 게시하지 않는다. 공개 저장소의 artifact 자체는 권한 격리된 비공개 관리자 저장소가 아니므로 민감정보를 적재하지 않는다.

## 범위 제한
이번 단계는 **진단 가시성 강화**이지 실패한 파이프라인을 임의로 재실행하거나 점수를 재계산하는 작업이 아니다. 수집 엔진·DB 발행 로직·홈페이지·Supabase·Cloudflare 설정과 Secret을 변경하지 않는다. 자동 점검 결과는 기록 시점의 스냅샷으로서, 실시간 화면이 아니다.

## 운영 검증
(1) PR QA 통과와 main 병합 (2) 최초 09:30 종합점검의 `bridge-reliability.json`에서 `stages` 확인 (3) 함께 첨부된 HTML의 '작업별 진단·실패 단계' 확인 (4) 실제 장애 발생 시 실패한 단계 명칭 및 GitHub Actions 실행 기록 대조.

첫 정기 점검 결과를 확인하기 전에는 실제 장애 진단 효율성이 입증되었다고 주장하지 않는다.
